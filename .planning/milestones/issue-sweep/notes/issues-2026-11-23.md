## Issue 31: A test fails instead of skipping when GND lacks its synth extra

Opened 2026-11-21.

`tests/test_tools.py::test_suggestions_and_generated_cases_with_newer_gnd` fails on a machine
whose GND is installed without its optional `synth` extra. It should skip there, as the
other GND tests skip when GND is missing.

### What happens

With `get-nick-done==0.4.0` installed by `uv tool install get-nick-done==0.4.0` (no
`[synth]`):

```bash
uv run --no-project --with pytest python -m pytest tests -q
```

gives `1 failed`, this test. The `rules test` step prints:

```text
note: gnd synth --guarded-cases built no cases (exit 5): ERROR: the synthetic-value generator needs the optional 'synth' extra.
```

so the test's last assertion (`wrong: cannot_fail can never fail`) does not hold.

### Why

The skip guard, `offered("synth", "--guarded-cases")`, checks only that `gnd synth --help`
lists the flag. A GND without the extra lists it too, and refuses only when the command
runs. `rules_check.py` itself is right here: it turns the refusal into a `note` and goes on.
Only the test assumes that a listed flag can run.

The failure has shown up as a known red in every full-suite run of the component-index
milestone (`.planning/milestones/component-index/001-plan.md`, R5), so a real failure in
that test would now pass unnoticed.

### Asked for

- The guard asks GND whether `synth --guarded-cases` can run, for example by running it once
  on a one-rule model and skipping on exit 5 with "needs the optional 'synth' extra".
- A test for the guard, with a fake `gnd` that lists the flag and exits 5.

### Workaround today

Install GND with the extra:

```bash
uv tool install --force 'get-nick-done[synth]==0.4.0' --with pytest==9.1.1
```

## Issue 33: In a dvt-milestone install, rules_check.py test fails on its own starter rules

Opened 2026-11-22.

### What happens

In a dvt-milestone install, `rules_check.py test` fails on the starter rules that
`rules_check.py init` has just written:

```
wrong: plan_names_the_components_it_touches: the failing example 1 names plan_names_component, task_in_plan, task_touches_component, which no fact type of this project is
wrong: plan_names_the_components_it_touches: the passing example 1 names plan_names_component, task_in_plan, task_touches_component, which no fact type of this project is
rules test: 6 rule(s), 12 example(s); 2 wrong
```

It exits 1. The same steps with the dvt-phase copy print `0 wrong` and exit 0.

### Why

In a plugin install, `rules_check.py` sets its default `phase_script` to
`<plugin>/skills/process-phase/scripts/phase_tool.py` (`skills/components/scripts/rules_check.py:256`).
dvt-milestone ships the components skill but no `phase_tool.py`
(`find plugins -name phase_tool.py` lists only dvt-phase's). `test` loads the plan fact
types from that file, and when it is absent they are dropped without a word
(`rules_check.py:791`), so the starter rule about plans names fact types that do not
exist. `check --phase` refuses with exit 2 and says it "is for a project that uses the
phase workflow", which may be intended; `init` and `test` give no such warning.

### Reproduce

In an empty git repository with one package (`src/app/__init__.py`), with GND 0.4.0 on
PATH:

```bash
python3 <dev-tools>/plugins/dvt-milestone/skills/components/scripts/components_index.py init
python3 <dev-tools>/plugins/dvt-milestone/skills/components/scripts/rules_check.py init
python3 <dev-tools>/plugins/dvt-milestone/skills/components/scripts/rules_check.py test
```

### What would fix it

One of: dvt-milestone's `init` leaves out the plan rule when no phase tool is there; or
`test` skips a rule whose fact types belong to a tool that is not installed, and says so;
or dvt-milestone ships the phase tool. A test that runs `init` then `test` on each plugin's
copy would catch it again.

Found while building dev-tools' own component index (component-index milestone, phase 3;
`.devtools/components/REVIEW.md`, suggestion 4).

## Issue 39: components: the index cannot see one script running another at run time

Opened 2026-11-23.

### What happens

The component index builds its graph from `import` statements. dev-tools' scripts import nothing from each other, because a synced script must stand alone, but five of them run or load another at run time:

| From | To | How |
|---|---|---|
| `devtools/release_plugins.py:35` | `build_plugins.py` | `importlib.util.spec_from_file_location` |
| `skills/components/scripts/rules_check.py:792` | `phase_tool.py` | `importlib.util.spec_from_file_location` (for `test`) |
| `skills/components/scripts/rules_check.py` | `components_index.py facts`, and `phase_tool.py facts` for `check --phase` | subprocess |
| `skills/phase/process-phase/scripts/phase_tool.py:1046` | `coder_pool.py show --json` | subprocess |
| `skills/phase/process-phase/scripts/phase_tool.py:1281` | a project's generator script | `runpy.run_path` |

So in dev-tools' own index:

- `review` lists every one of the 12 components under "Components nothing in the package imports";
- it lists the steps of all three subsystems under "Flow steps that no earlier step imports";
- `uses` and `used_by` are `(none)` for every entry.

The three subsystems state the loads by hand in `notes:`. Nothing checks those notes against the code.

### What would help

Let the script read the calls it can read without running anything: `importlib.util.spec_from_file_location(...)` and `runpy.run_path(...)` whose path is a literal or built from literals, and a `subprocess` call whose argument names a sibling `.py` file. Record each as an edge marked as a run-time load, so `uses`, `used_by` and the flow check can count it, and `review` can still tell it from an import.

A path computed at run time (a setting, a project's own script) stays invisible, and the docs should say so.

This is a change to the product, for every project that keeps an index.

Raised at the close of the `component-index` milestone: `.planning/milestones/component-index/007-close.md`, proposed issue P1 (its question Q1).

## Issue 40: dev-handoff: keep the ignored paths of a hand-off note in a form takeover can parse

Opened 2026-11-23.

### What happens

`handoff.py write` puts the list of ignored paths into the note as Markdown bullets written for a person. `handoff.py takeover` reads those bullets back to decide whether a checkout is ready. Eight review rounds of the `component-index` milestone each found a note that reads as ready while an ignored path is missing:

- a path holding a backtick, then one holding a newline (plan review, rounds 2 and 3);
- three more ways a path failed to survive the bullet format (phase 1, rounds 1 and 2);
- a Unicode line separator, an empty path that names the checkout itself, and a file named like the snapshot's end marker (phase 1, round 3);
- a paused-phase folder whose name forges the snapshot's own lines (phase 1, round 4);
- a rest line whose "and N smaller paths" line was deleted by hand (phase 3, round 4);
- a git remote whose path holds line breaks (the review of #37; fixed in #38).

Each was fixed, and each fix closed the cases its round found. #38 is wider: every line the writer generates is kept to one line. A note edited by hand is still read as Markdown.

Before #38, a close review ran the writer and the reader over 516 in-memory scenarios and found nothing. The next reviewer found the remote.

### What would help

Write the whole inventory in the note in a form a parser reads, and have `takeover` read only that. The note already does this for the paths after the 25th: `<!-- ignored-rest: [...] -->` is one JSON line. The same line could hold every path, with its kind (carry, large, key). The bullets would stay, for the reader, and `takeover` would stop reading them.

### What it changes

- The note's format, which branches of other projects already hold. `.devtools/project.md` puts such a change in the evidence lane, so this is a milestone, not a fix.
- A note from an older version has no such line. It should read as not ready, with a count of what could not be checked, as a cut list from 0.1.3 does today.
- Whether a hand-edited inventory line is trusted, or checked against something (a digest in the frontmatter), is the design question to settle first.

Raised at the close of the `component-index` milestone: `.planning/milestones/component-index/007-close.md`, proposed issue P2 (Q3). `008-close-correction.md` beside it has the last case.

## Issue 41: sync.py and from_gsd.py each carry the same list of other planning tools

Opened 2026-11-23.

### What happens

`OTHER_PLANS` is the same list of 8 entries in `devtools/sync.py:454` and `devtools/from_gsd.py:46`, and each file has its own `other_plans` function that walks it (`sync.py:459`, `from_gsd.py:489`). A change to the list has to be made twice.

Checked on `main` at `a8d6f42`: the two lists compare equal.

### What would help

One list, in one place. Both scripts live in `devtools/` and run from a dev-tools checkout; neither is copied into a project, so the rule that a shipped script stands alone does not hold them apart.

### What could break

The two functions are not the same. `from_gsd.py`'s returns `{"tool", "sign"}` dictionaries and `sync.py`'s returns `(sign, tool)` pairs, and `sync.py`'s also flags a planning folder in a format the phase tool does not read. So the list can be shared as it is; the functions need their callers looked at first.

dev-tools' own index records this as `duplicates: devtools/from_gsd.py` on `sync.copies`.

Raised at the close of the `component-index` milestone: `.planning/milestones/component-index/007-close.md`, proposed issue P3 (Q7, suggestion 1 of `.devtools/components/REVIEW.md`).

## Issue 42: No test runs the phase_selection.py pytest plugin

Opened 2026-11-23.

### What happens

`skills/phase/pytest/phase_selection.py` is a pytest plugin that a project uses as its root `conftest.py`: `pytest --phase NN` runs one phase's acceptance tests, and plain `pytest` leaves out the phases that are not complete. No file under `tests/` names it (`grep -l phase_selection tests/*.py` prints nothing), so nothing here would notice if it stopped selecting the right tests.

It is the one module of the 12 in dev-tools' index with no test listed.

### What would help

A test that makes a small project with the plugin as its `conftest.py`, with acceptance tests of a complete phase and of an open one, runs pytest there, and checks what is collected:

- plain `pytest`: the complete phase's tests, not the open one's;
- `pytest --phase NN`: that phase's tests;
- an acceptance test named by path runs whatever its phase's state (the plugin lets a named path win).

`tests/test_plugins.py` already runs scripts in a new project made under `tmp_path`, and is the shape to follow.

Raised at the close of the `component-index` milestone: `.planning/milestones/component-index/007-close.md`, proposed issue P4 (Q7, suggestion 2 of `.devtools/components/REVIEW.md`).

## Issue 44: components: review's same-name leads ignore the folders count_extra_dirs counts

Opened 2026-11-23.

### What happens

Since 0.1.5, `count_extra_dirs` makes `--check --strict`, `stats`, `draft`, `changed` and `review`'s "Modules with no component" count the modules of `extra_source_dirs`. `review`'s other groups were left as they were: they are built from the package alone (`skills/components/scripts/components_index.py:1317`, `package = … sources(root, PACKAGE_DIR)`).

One of them is "The same public name in two or three components (a duplicate?)". With `package_dir: devtools` and `extra_source_dirs: [skills]`, as in dev-tools, it looks at 4 of the 12 modules. Six scripts under `skills/` each define `plugin_root`, `checkout_root` and `load_settings`, and `review` says nothing about them; they were found by reading.

### What would help

When `count_extra_dirs` is on, build the same-name group over `counted_modules(root)`, as the no-component group already is.

The groups that come from the import graph (components that import each other, loops, flow steps) are a separate matter: the graph stays within `package_dir` on purpose.

### What could change for a project

A project that turns the setting on would see new leads in that group. They are leads to look at, not failures: `review` always exits 0. `distinct_from` on the entries says two same-named definitions are separate on purpose.

Raised at the close of the `component-index` milestone: `.planning/milestones/component-index/007-close.md`, proposed issue P6 (Q10, suggestion 5 of `.devtools/components/REVIEW.md`).

## Issue 45: components: changed can judge against a stale local base, and an entry cannot be marked as reread

Opened 2026-11-23.

Two things about how the index tool decides what a change touched. They came up together and can be fixed apart.

### 1. `changed` compares with a local `main` that nothing moves

`changed --base` defaults to `main` (`skills/components/scripts/components_index.py:1552`). It uses the local branch of that name when there is one, and `origin/main` only when there is not (`:1089-1092`), then takes the merge base with `HEAD`.

In a git worktree the local `main` belongs to another checkout, and nothing in the worktree moves it. During the `component-index` milestone it was eight days behind:

```
changed against main (b685e82): 171 file(s) differ; 0 to fix, 0 warning(s), 0 to reread
changed against origin/main (827e766): 9 file(s) differ; 0 to fix, 0 warning(s), 0 to reread
```

The first run judged 171 files for a 9-file change. It is never less than the change, so it does not hide a failure, but its `reread:` lines would name other people's work. dev-tools' own gate row now says `--base origin/main`, after a fetch.

**What would help:** when the base is a local branch that is behind its remote-tracking branch, say so in one line and name the command to use; or prefer the remote-tracking branch when both exist. Nothing should fetch: the command reads only.

### 2. `review` keeps listing an entry that was reread and found true

"Descriptions older than their code" dates an entry by when its `does` and `verbs` lines were last edited, and counts the commits to its modules since. After a change that keeps behaviour (#34 reformatted strings in three scripts), the entries of those modules are listed:

```
handoff.notes: 3 commit(s) to its modules since 27ca753 (2026-11-22), when its does and verbs were last edited
components.rules: 1 commit(s) to its modules since 176d7a4 (2026-11-22), when its does and verbs were last edited
```

Both were then read beside #34's diff and are still true. They stay on the list, because nothing in `does` or `verbs` changed, and they will stay until someone edits a line that did not need editing.

**What would help:** a way to record that an entry was read against the code at a commit without changing what it says: a field the script reads (a commit or a date), or counting an edit to `notes:` as well. `changed`'s `reread:` lines would follow the same rule.

Raised at the close of the `component-index` milestone: `.planning/milestones/component-index/007-close.md`, proposed issue P7 (Q13 and Q15).

## Issue 46: components: --check --strict cannot refuse a baseline file

Opened 2026-11-23.

### What happens

`--check --strict` fails on a module that no component covers, except the modules named in `<docs_dir>/unassigned-baseline.txt` (`skills/components/scripts/components_index.py:961-963`). `stats --write-baseline` writes that file. This is what lets a large project start an index and shrink the list over time.

A project that has reached full coverage has no way to say "and keep it that way". If a baseline file appears, the strict check excuses whatever it names and still exits 0. Reproduced in a copy of dev-tools:

1. add a module no entry lists;
2. run `write`, then `stats --write-baseline`;
3. `--check --strict` exits 0 and prints nothing.

dev-tools' completion check had to be written as two commands for this reason (`--check --strict`, and `test ! -e …/unassigned-baseline.txt`), and its test checks for the file itself (`tests/test_own_index.py`).

### What would help

One of:

- an option, for example `--check --strict --no-baseline`, that fails when the baseline file exists;
- a setting in `components_index.settings.json` with the same effect, so the project's gate command stays as it is.

The default must stay as today: a project with a baseline keeps passing.

Raised at the close of the `component-index` milestone: `.planning/milestones/component-index/007-close.md`, proposed issue P8 (Q14).
