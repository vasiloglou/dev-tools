---
name: adopt-devtools
description: Replace a project's own copies of the development-process skills (phase workflow, milestone workflow, component index, helper agents) with the shared dev-tools versions, without losing the project's own rules. Use when asked to adopt dev-tools in an existing repository, to migrate or replace its process skills, or to bring a project that drifted back onto the shared skills. Surveys what the project has, writes its .devtools.toml, shows every line a replacement would drop and everything the shared text adds, moves the project's rules into the files it owns, applies the sync, removes the old copies and checks the project still passes what it passed before. Not for a new project (use the example .devtools.toml) or for a routine update of files that are already synced (run sync.py apply).
---

# adopt-devtools

A project that grew its own process skills holds two things in one text: the process,
which dev-tools now ships, and the project's own rules, which dev-tools does not know.
Replacing the files whole (`apply --adopt`) loses the second. This skill replaces them
so that every line the project had is still stated by the shipped text, moved to a file
the project owns, or dropped on purpose and written down; and so that everything the
shipped text adds has been read against how the project works.

It is read from the dev-tools checkout, not copied into the project. Below, `<dev-tools>`
is the checkout that holds this file, commands run from the project's root, and `sync`
stands for `python3 <dev-tools>/devtools/sync.py` (Python 3.11 or newer).

| Command | What it does | Writes? |
|---|---|---|
| `sync survey --project .` | Finds the project's copies of what dev-tools ships, the project's own skills, and old copies under another name | No |
| `sync survey --project . --toml` | Prints a starter `.devtools.toml` that delivers each shipped unit to the place the project keeps its copy | No |
| `sync compare --project .` | One row per file: `new`, `replace`, `update`, `edited`, `remove`, `kept` (excluded), `old copy` (under `replaces`); and how many of the project's lines are in no shipped file | No |
| `sync compare --project . <path> …` | The lines only the project's copy has, with line numbers, the heading they sit under, the shipped line a line is close to (`~ shipped:`), and the project-owned file a line is now in (`[in …]`). `--added` prints the other side, the lines only the shipped file has; `--diff` prints the full difference | No |
| `sync compare --project . --record` | The table for the migration record, one row per file, with the counts filled in | No |
| `sync apply --project . --adopt [--dry-run]` | Replaces the files and writes the receipt. It calls the same files `create` and `update` | Yes |
| `sync check --project .` | Confirms the synced files are what was delivered | No |

## Rules

- Work on a new branch of the project, from a clean working tree. Never on its base
  branch. If `git status --short` shows changes to tracked files, stop and ask.
- You may change only:
  - `.devtools.toml`, the receipt, the synced paths, and the record of this migration
    (step 6 says where it goes);
  - the project-owned rule files (`references/project.md`, the instruction files);
  - the old copies you remove, and pointers to a renamed skill, wherever they are (the
    name itself, also inside one of the project's own skills; a record of history, such
    as a decision row, is left as it was written);
  - what the project's own bookkeeping requires when process files change: a generated
    file regenerated by the project's command, a decision row, a manifest;
  - a pin of the file set: a test or inventory that lists these folders' files, changed
    only as far as the new file set requires.
  Nothing else. No product code, and no other test.
- Never edit a synced file by hand, and never use `--force` here. A synced file that
  does not fit the project is fixed with a setting, a line in `project.md`, or `exclude`.
- The project's own skills (the survey's "no counterpart" list) are not otherwise touched.
- Do not push, merge or open a pull request unless the user asked for it.
- A line is dropped only after you have read it. "Probably old wording" is not a reading.
- **Running unattended.** Where a step says to ask or tell the user and nobody is there,
  take the choice that changes the project's behaviour least, go on, and put the
  question first in the record and in your report. Two cases have a fixed answer: an
  agent file that would lose a line only it can hold is excluded; a skill's entry file
  (`SKILL.md`) is taken as shipped, because it is what points to `project.md`, and the
  lost line is recorded as a Gap.

## 1. Survey

```bash
python3 <dev-tools>/devtools/sync.py survey --project .
```

| Section | Meaning | What to do |
|---|---|---|
| Counterparts | A folder or file here is the project's copy of a shipped unit. The percentage is the share of the shipped `SKILL.md` lines the project's copy also has; "not here" names shipped files the copy lacks | These are replaced. A copy marked "dev-tools names it …" is delivered under the shipped name, and the old folder is removed in step 7 |
| Shipped files the project keeps outside its copy of the skill | A shipped script that lives elsewhere here (often `scripts/`), or a shipped file whose content the project keeps in another place | A script is delivered there, once, and excluded from the skill's folder. Any other file is a question for step 5: the project may already have this contract somewhere it is tested |
| Shipped, with no counterpart here | Units the project does not have. The survey matches a standalone file by name, so the project's version may exist under another name or as part of a larger file | Leave them out unless the user wants one. If the project has its own version inside a larger file, leave it out too and name the project's mechanism in `project.md`. Mention them in the report |
| Same name, different skill | The project has a skill of its own under a name dev-tools also uses | Do not sync to that path. Ask the user: rename theirs, or leave the unit out |
| The project's own skills | Not part of this | Nothing |
| Symlinked skill folders | Skills installed by something else | Nothing |
| `[not tracked by git]` | The folder is ignored or was never added | Leave it out of the config unless the user wants it committed |
| To find what reads these copies | A `git grep` line with the names that point at the copies | Used in step 2 |
| A plan kept by another planning tool | Spec Kit, OpenSpec, Kiro, BMAD, Task Master or Agent OS files, or a `.planning/` whose roadmap or state the phase tool did not write | No tool moves it. See "Coming from another planning tool" at the end of this file |
| A planning folder written by GSD | `.planning/` holds a GSD plan | This skill covers the project's copies of the skills only. The plan is moved with the `move-from-gsd` skill (`<dev-tools>/skills/move-from-gsd/SKILL.md`); never run `phase_tool.py setup` on it |

In a git project the survey reads the files git tracks or would track, plus the skill and
agent folders at the top (`.claude/skills`, `.codex/agents`, `skills` …) whatever git
says. A copy kept in an ignored folder anywhere else is not found: name it yourself.

A project that serves more than one agent runtime has one counterpart per runtime
folder (`.claude/skills`, `.codex/skills`, `.agents/skills`). Confirm the copies are
identical now (`diff -r`); if they are not, find out which one the project treats as
the source before going on. Each folder gets its own entry, so the copies stay identical.

Tell the user which units will be replaced and where, and which are left out, before
going on. If the survey finds no counterpart, this is not a migration: use
`examples/phase-project.devtools.toml`.

## 2. Before anything changes

1. **The source.** `git -C <dev-tools> status --porcelain -- skills agents devtools`
   is empty and you know its commit (`git -C <dev-tools> rev-parse --short HEAD`). The
   sync also warns when the files it delivers have uncommitted changes; a migration
   from such a checkout cannot say what it delivered, so stop and ask.
2. **What passes today**, so that step 8 can tell a new failure from an old one. Keep
   the output of each:
   - the process tool's check, where the workflow has one (`phase_tool.py check --all`);
     and a second checkout of the project as it is now, for the side-by-side run in
     step 8 (`git worktree add <temp folder> HEAD`; a script needs the files around it,
     so a copy of the script alone does not run);
   - the component index check, if the project has an index;
   - the tests that read what will be replaced. Run the `git grep` line the survey
     prints last: it searches the whole project for the folders, script names and data
     files of the copies. From the hits take the tests (a hit in a helper means the
     tests of that folder), and the scripts and CI files that import or load a replaced
     script as a module: those depend on its functions, not only on its commands, and
     their tests belong in the set. Add any test that lists the files at the project's
     root or globs the skill folders (`git grep -l -e 'skills/\*' -e 'glob(\"\*.md' -- tests`);
   - for a workflow with no process tool (the milestone workflow), the state of the
     planning folder instead: `git rev-parse HEAD:<planning folder>` and the last record
     of each milestone.
3. **Where work stands**: the current phase or milestone and its step. The migration
   must leave it exactly there.
4. Create the branch.

## 3. Write `.devtools.toml`

```bash
python3 <dev-tools>/devtools/sync.py survey --project . --toml > .devtools.toml
```

The starter keeps the project's paths. The sync refuses to run while a `"TODO"` is
left, and that is on purpose: the shipped scripts take from settings what the project's
own copies had written into them, so every setting is a decision about this project.

- **`"TODO"` with a default in the comment.** Read the project's copy of the script to
  see what it did, and the setting's comment in the shipped script to see what the
  value means (the lines above the block name both), then write the value. The
  default is right only if the project's copy did the same. An empty value is valid
  where the comment says so. Watch for settings that switch something on or off: a
  list of extra folders, the path of a second script the tool runs, the first step
  that blocks.
- **"read from …"** means the survey found the value in the project's copy (a constant
  of the same name, or a shipped line with the value filled in). **"from the survey"**
  means it follows from where things are. Check both: `skill_roots`, for example, holds
  only the folders with a counterpart, and the project's check may have covered more.
- **`skill_check`** says which skills and agents `check --all` holds to the skill
  rules. `"all"` checks every skill under `skill_roots` and every file in `agents_dir`;
  that is right only if the project's own skills and agents were written to those rules
  (a name equal to the folder or file name, a description, every referenced file
  present). Otherwise write `"synced"`: only what the sync delivered is checked.
- **A folder that is a link.** The sync refuses a destination that passes through a link
  out of the project, and two destinations that are one file (one runtime's skills
  folder linked to another's). Deliver to one of the two; the link serves the other.
- **`values`** fill `{{devtools:<name>}}` in shipped text. The milestone workflow needs
  only these; it ships no script and has no settings.
- **`replaces`** names an old copy under another name, so that `compare` reads it.
  Nothing deletes it; you do, in step 7.
- **A command to run after a sync.** If a synced script generates files (the component
  index does), uncomment the `after_apply` line at the top and give it the interpreter
  and the script's path as the project runs it. It runs without a shell: to set a
  variable write `env NAME=value <command>`.
- **Data files that differ.** The starter lists, under an entry, the data files in the
  project's copy that differ from the shipped ones (a gates file, for example). Decide
  each in step 4: `exclude` it if its content is the project's.
- Remove the entries for units the user left out, and the trailing comment list.

## 4. Compare, and decide what happens to every line the project has

```bash
python3 <dev-tools>/devtools/sync.py compare --project .
```

Each `replace` row is a file of the project's that would be overwritten; each `old copy`
row is a file that will be deleted. The number is how many of its lines are in no file
the sync delivers (a sentence that was only re-wrapped is not counted). Those lines are
what the project can lose. A copy in a second runtime folder that is byte for byte the
same is counted once ("same as …"). For each file with a number:

```bash
python3 <dev-tools>/devtools/sync.py compare --project . <path>
```

A line followed by `~ shipped:` has a close relative in the shipped file: read the two
and see which words changed. A line with no relative may still be stated elsewhere in
other words, or be half of a sentence that was wrapped differently: check before you
call it the project's alone. A heading that only the project has is listed and counted
like any other line. Use
`--diff` whenever you need the surroundings. Scripts and data files are not listed line
by line: read them with `--diff`, and for a script ask two questions: which of its
hard-coded values does a setting now carry, and what does it do that the shipped one
does not.

Give each run of lines one outcome:

| Outcome | When | What you do |
|---|---|---|
| **Stated** | The shipped text states the same rule in other words | Note where (file and heading) when it is not the `~ shipped:` line. Nothing to carry |
| **Carried** | A rule of this project: it names the project's modules, commands, paths, gates, reviewers, limits, or a constraint only this product has. A rule about which areas of the code may use which can also go, checked, into `docs/components/layers.toml` (`components` skill, "Project rules"), if the user wants the optional check | Move it to `references/project.md` (below) |
| **Kept file** | A whole file whose content is the project's: a data file a script reads, a file of the project's examples | Add the file to `exclude` for that entry. It then shows as `kept`. Improvements to the shipped one will not arrive, so say so in the report |
| **Changed** | The shipped text states a different rule on the same point | The shipped rule wins unless the user says otherwise. Check whether existing records or files rely on the old rule, list both rules in the record, and ask the user |
| **Gap** | The project's copy does something the shipped one cannot, and no setting covers it: a script's behaviour, or a line that only a synced file can hold (a skill's `allowed-tools`, an agent's `skills:`) | Do not lose it silently. For an agent file or a data file, keep the project's with `exclude`. For a skill's `SKILL.md`, take the shipped file and record what is lost: a permission the project needs can be granted in its agent settings, which is the user's change to make. Report every gap so it can be raised with dev-tools |
| **Candidate** | A general process rule, not specific to this project, that the shipped text lacks | Carry it to `project.md` for now and list it in the report as something dev-tools could take |
| **Dropped** | It refers to something the project no longer has, or records history that has no force | Drop it, and list it in the report with the reason |

When unsure between Stated and Carried, carry it: a rule said twice costs a line, a rule
lost costs a mistake nobody can trace.

**Where carried rules go.** Every shipped skill and agent that has project-specific
matter points to one file: `references/project.md` in the `process-phase` skill's
folder. The project owns it and the sync never touches it. Before writing, list what
the shipped text expects it to answer:

```bash
grep -rn 'project\.md' <dev-tools>/<each source you take>
```

Each hit names something (a test command, a review instrument, the plan-review bar,
invariants, required reading, release gates). Give `project.md` a heading for each one
the project has an answer to, put the carried rules under the heading for the step or
file they applied to, and for each hook you leave unanswered read the default the
shipped text then applies: leaving it silent is a decision too.

- **Start the file with two lines for future agents**: these skills are synced from
  dev-tools and are never edited here (`sync check` fails if they are); project rules
  go in this file. If the project's instruction file (`CLAUDE.md`, `AGENTS.md`)
  describes how skills are maintained, add one line there too.
- **Move text close to how it was written**, regrouped. A measured fact or a piece of
  history behind a rule is not a rule: keep one line and a pointer. Correct a stale fact
  while carrying it (name the function, not a line number that has moved) and say so in
  the record. Many lines that only cite a decision id become one table of ids.
- **Keep it short enough to be read at the start of every step.** Past about 300
  lines, put a whole topic in a second project-owned file beside it and point to it.
- A project with several runtime folders keeps one identical copy in each.
- If a skill is used outside the workflow (the component index often is), add a pointer
  to `project.md` in the instruction file, so its rules are found there too.
- An agent that is given only a brief reads `project.md` only if its text says so. For
  a rule such an agent needs, tell the supervisor in `project.md` to put it in the brief.

`compare` then marks `[in …]` each line that is now in a project-owned file, word for
word or nearly. A rule you reworded, merged or put in a table is not marked, so the
record, not the mark, is what accounts for every carried line.

## 5. Read what the shared text adds

The list in step 4 shows only what the project loses. The other half is what arrives:
rules, defaults and formats the project never had. Read, against how the project works
today (its records and files, not only its skill text):

- **Every `new` row.** Does the project already keep this content somewhere else (the
  survey's "keeps outside" section)? Two copies of one contract will drift; decide
  which is the source, and say so in `project.md`.
- **What arrives in each replaced file**: `sync compare --project . <path> --added`
  prints the lines only the shipped file has, under their headings. Read them for
  names and formats: file names of
  records, field names, status words, branch names. Where they differ from what the
  existing records use, the project's go in `project.md`; existing records are never
  rewritten to match.
- **Defaults that apply when `project.md` is silent** (the hooks listed in step 4).
- **New stops and duties**: an approval the project did not ask for before, a file that
  must now exist at a step, a check that now blocks.
- **Scripts.** A script's added lines are too many to read as text. Read the commands
  that write (the ones that move a phase or a record forward): what does each decide,
  and does the project's state contain a case the old script treated differently? Step
  8 runs them.

Each one gets a line in the record: accepted as shipped, answered in `project.md`,
excluded, or a Gap.

Also look for things that pin the old files:

- **Files only the project has** inside a synced folder (the last block `compare`
  prints). An apply leaves them. Decide for each: still referenced by a rule you carried
  (keep), superseded by a shipped file under another name (remove in step 7), or the
  project's own (keep).
- **Pointers to a renamed skill.** `git grep -n '<old name>'` across the project:
  instruction files, other skills, docs, CI, tests. Update each to the new name, except
  in records of history.
- **Bookkeeping the project attaches to process files**: a file generated from skill
  descriptions, a rule that a change to process text needs a recorded decision, a
  manifest of files. Follow it: regenerate, add the row. A decision row that needs an
  approver you do not have is written as pending the user's approval of the merge, and
  flagged at the top of the record.
- **Digests.** If the project's records cite the SHA-256 of a replaced file
  (`shasum -a 256 <file>`, then `git grep` the first 16 characters), list where. Records
  of history stay as they are; a check that compares them with current bytes is a pin.

## 6. The record

Write the outcomes down as you go, in `.devtools-migration.md` at the project's root,
or where the project keeps such documents if a check restricts what may sit at the root.
`sync compare --project . --record` prints the table with the first two columns filled
and a total.

```markdown
# Moving to the shared dev-tools skills

Source: dev-tools <commit>. Project at <commit>. Units replaced: <list>. Left out: <list>.

## Questions for the owner
<anything that needs a decision: Changed rules, Gaps, pending decision rows>

| File | Lines only here | Stated | Carried | Kept file | Changed | Gap | Candidate | Dropped |
|---|---|---|---|---|---|---|---|---|

## Carried
<each rule in one line, with where it came from and where it is now>

## Changed, gaps, candidates and dropped lines
<each with the reason>

## What the shared text adds
<each new file, name, default and duty, with what was decided>

## Checks
<what passed before, what passes after>
```

The numbers in a row add up to the file's count. A project with several identical
runtime folders has one row per file. The record is for whoever reviews the change;
nothing reads it afterwards.

## 7. Apply, and remove what is left over

```bash
python3 <dev-tools>/devtools/sync.py apply --project . --adopt --dry-run
```

```bash
python3 <dev-tools>/devtools/sync.py apply --project . --adopt
```

```bash
python3 <dev-tools>/devtools/sync.py check --project .
```

Then `git add` the new paths and run `compare` and `survey` again:

- `compare` shows no `replace` row. Its "only in the project" block holds what you
  decided to keep, and nothing else: remove the superseded files now (`git rm`).
- `survey` marks each delivered copy `[synced]`. A counterpart marked as the old copy
  named under `replaces` (or `[not in .devtools.toml]`) is what is left to remove:
  confirm nothing points to it any more (`git grep`), `git rm -r` it, and take the
  `replaces` line out of the config. Never remove a folder git does not track.

## 8. Check the project still works

Stage the change first: some projects' tests read `git ls-files`.

1. Run again everything from step 2.2. A failure that was not there before is caused by
   the migration. What to do depends on what failed:
   - **A setting or a rule is missing**: fix it with a setting, a line in `project.md`
     or an `exclude`.
   - **A pin of the file set** (a test or inventory that lists these folders' files):
     update the pin as far as the new file set requires.
   - **The project's own check on skill text** meets something in the shipped wording
     (an example path that does not exist here, a name the check does not know): that
     is a defect to report to dev-tools. Until it is fixed there, the choices are the
     user's: exempt the synced paths in the check, or wait. Leave it failing and put it
     first in the record.
   - **The project's tests of a replaced script's internals**: those tests now belong
     with the shipped script. Whether to drop or trim them is the user's decision; a
     difference in what the script does for the project is a Gap.
   - **Anything else** is a Gap.
   Never fix a failure by editing a synced file: `check` would then fail, and the next
   update would undo it.
2. Run the old script in the second checkout (step 2.2) and the new one here, side by
   side, on the read-only commands (status, list, check): the output is the same, or
   you can say why it differs. Then, in two throwaway checkouts (one of the old commit,
   one of this branch), run the command that writes next in the project's work (the
   next advance or close) with each script and compare what it decides. A difference is
   a Changed rule or a Gap. Remove the checkouts afterwards (`git worktree remove`).
3. Work stands where step 2.3 noted: the same phase and step from the process tool, or
   an unchanged planning folder (`git rev-parse HEAD:<planning folder>` after the
   commit; before it, `git status --short <planning folder>` is empty).
4. Read the shipped `SKILL.md` and then `project.md` the way an agent starting the next
   step would. For each Carried rule in the record: is it reachable from what is read at
   the step it governs? For each hook from step 4: answered, or left to a default you
   have read? Move or add what is missing.
5. `git status --short`: every changed path is one the Rules allow.

## 9. Finish

Fill the Checks section of the record, commit on the branch (the message names the
dev-tools commit), and if any test reads Git history, run those tests once more after
the commit. Show the user:

- what was replaced, at which paths, and what was left out;
- the questions for the owner, first;
- the totals per outcome, and every Changed, Gap, Candidate and Dropped line with its reason;
- what the shared text adds and what was decided for each;
- what passed before and after, and anything you could not run;
- what remains for them: review the record, merge, and from then on `sync apply` for
  updates (`sync compare` first shows what an update would change).

If you ran unattended, the questions the Rules told you to carry are at the top of the
record and of your report.

## Coming from another planning tool

Only GSD has a converter (`move-from-gsd`). For any other tool that keeps a plan in the
project (the survey names Spec Kit, OpenSpec, Kiro, BMAD, Task Master and Agent OS, and a
`.planning/` folder in a format the phase tool does not read), the plan is carried by
hand. The steps above still cover the project's copies of the skills; these cover the
plan.

1. **Keep the old plan readable.** Leave the other tool's folders where they are. If
   `.planning/` itself holds the old plan, `git mv` its files to `.planning/archive/<tool>/`
   first: `phase_tool.py setup` stops with `FOREIGN_PLAN` while a `STATE.md`,
   `ROADMAP.md` or `REQUIREMENTS.md` in another format is there, and it never
   overwrites a file.
2. **Run `phase_tool.py setup`** once the skills are synced. It writes the planning
   files with one placeholder phase.
3. **Write the roadmap from the old plan**, one `## Phase N: Title` block for each unit
   of work the old tool had (a spec, a change, an epic, a milestone), in the format of
   `references/artifact-formats.md` in the process-phase skill:

   | The old plan has | It becomes |
   |---|---|
   | A unit that is built and accepted | A phase with `Status: complete` and `Acceptance tests: none: finished under <tool>`, with a link to its old record. Add its number to `completed_phases` in `STATE.md` |
   | A unit that is specified and not built | A phase with `Status: not_started`. Its spec is input to the phase's discussion; link it from the phase's goal |
   | A unit half built | Finish it under the old tool first, or make it a `not_started` phase and say in its goal what exists |
   | Requirements or user stories | Rows of `REQUIREMENTS.md`: a `U` row for each need, a `REQ-<FAMILY>-<number>` row for each requirement, with its phase |
   | A constitution, principles or standing rules | `MANIFESTO.md` for what must always hold; `references/project.md` for how the work is done here |
   | Recorded decisions | Rows of `DECISIONS.md` |

4. **Record the move** as a row in `DECISIONS.md`, with a second row that says the
   phases finished under the old tool stand as complete with no locked acceptance
   tests. `check --all` asks for neither file for a phase whose block says
   `Acceptance tests: none`.
5. **Run `phase_tool.py check --all`** and fix what it reports before the first phase
   starts. Take the other tool's commands, agents and hooks out of the project only
   with the user's go-ahead, as for GSD (`move-from-gsd`, step 6).
