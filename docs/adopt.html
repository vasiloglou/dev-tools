Add it to your project

One small file, one command, nothing to install.

The skills live in one place. Each project that uses them holds its own copy, checked in beside its code. You choose what to take, the copy is made for you, and a later update never silently overwrites something you changed.

Why a copy, and not a package

Skills are instructions an agent reads from your repository. A copy that is checked in means every teammate, every agent and every automated run sees exactly the same process, with no install step and no version to resolve. A contributor who cannot reach this repository can still work on yours.

Nothing to install

The skills are text files and a few small scripts. They run with what the project already has.

Your layout stays

Files land at the paths your project already uses. A project in mid-flight keeps its folders, its branch names and its history.

Changes are visible

An update to the process arrives as an ordinary change you can read and review before it is merged.

Both agents, one source

The same skill is copied for Claude Code and for Codex, byte for byte, so the two never drift apart.

Three steps

  1. Say what you want

    Add a file named .devtools.toml to the root of your project. Each entry names one thing to take and where it goes. The settings underneath are your project's own values: where planning files live, where tests live, how branches are named.

    To serve both agents, list the same skill twice with two destinations.

    # .devtools.toml
[[sync]]
source = "skills/phase/process-phase"
dest   = ".claude/skills/process-phase"

[sync.settings."scripts/phase_tool.settings.json"]
planning_dir   = ".planning"
acceptance_dir = "tests/acceptance"
package_prefix = "shelf"
branch_prefix  = "phase/"

[[sync]]
source = "skills/components/scripts/components_index.py"
dest   = "scripts/components_index.py"

    Shortened. The repository has a complete example file.

  2. Run the sync

    One command copies the files and writes a receipt that lists every file it manages, with a fingerprint of each. Nothing is written unless everything can be written.

    A second command checks, at any time, that the copies are still what was delivered. It needs only your project, so it can run in your automated checks.

    shelf · first synccaptured
    $ devtools-sync apply --project .
applied: {"create": 29}
after_apply: python3 scripts/components_index.py write

$ devtools-sync check --project .
29 managed file(s), 0 problem(s)

$ devtools-sync apply --project .
applied: {"keep": 29}

    29 files copied, then checked. Running it again changes nothing.

  3. Add your own rules, then commit

    The shared skills are written to know nothing about your product. What is specific to you goes in one file that you own and the sync never touches: references/project.md, beside the skill.

    Typical contents: the command that runs your tests, the rules that must never be broken, extra checks before a release, the reviewer you use. The agent reads it first, and it wins on anything project-specific.

    A rule about which parts of the code may use which has a second home where it is checked rather than read: docs/components/layers.toml beside the component index, which the sync never touches either.

    # .claude/skills/process-phase/references/project.md

## Commands
- Tests for one phase: `pytest tests --phase NN`
- Full suite: `pytest -q`

## Rules that must never break
- The export format is frozen; a change needs a decision record.
- No network access in tests.

## Before a release
- Run the packaging check.

    An example of a project-owned rules file.

Updates that respect your changes

When the shared skills improve, run the sync again. Files you have not touched are updated. A file you edited by hand is reported, and the whole update stops until you decide.

Someone adds a line to a synced rule. The check reports it, and an update refuses to overwrite it.

SituationWhat the sync does
File unchanged since last syncUpdates it
You edited a synced fileStops and names the file. Nothing is written until you choose to overwrite
A file already exists that it does not manageStops. You confirm before it takes the file over
You want to keep your own version of one fileList it under exclude; it stays yours
You added files beside the synced onesLeaves them alone
A file was removed upstreamRemoves your copy only if you had not changed it
Something must be rebuilt after an updateRuns the commands you listed, only when a file actually changed

Already have your own process skills?

A project that grew its own process holds two things in one text: the process, which is now shared, and its own rules, which nobody else knows. Overwriting the files would lose the second. So the agent looks first, and decides what happens to every line before anything is replaced.

Compare

See every line a replacement would drop

Before anything is written, the agent gets the list of files that would be replaced and, for each, the lines that appear in no shared file. Those lines are the whole risk of moving.

It reads each one and gives it an outcome:

  • Stated: the shared text says the same thing in other words.
  • Carried: a rule of yours. It moves to project.md, the file you own.
  • Kept file: a whole file of yours stays, and is left out of the sync.
  • Changed: the shared text says something different on the same point. Both are written down, and you decide.
  • Gap: your copy does something the shared one cannot. It is kept and reported.
  • Dropped: it refers to something that no longer exists. Written down with the reason.

Tried on real code. Agents moved two real projects in throwaway copies: one that works in phases (three skills, five helper agents and a script), twice, and one that works in milestones and keeps every skill in two agent folders.

Each had 450 to 700 lines of its own in the files to be replaced. About 200 of them were project rules and were carried into project.md; whole files of the project's own were kept; differences that needed a decision were put to the owner as questions.

The first run broke seven of the project's tests. The causes were in the shared files and are fixed. In the other two runs the same tests passed before and after. The three runs also logged 63 defects in the guide and its commands; most are fixed.

Coming from GSD?

A project planned with GSD already keeps its plan in .planning/, and names its phase folders and the files inside them the way the phase workflow does. So the phase folders stay exactly as they are. What changes is the format of three files, and GSD's own files move to an archive inside the planning folder.

Look

See what the move would do

One command reads the GSD planning folder and writes nothing. It lists every phase with the status it will get, the requirements and decisions it will carry, and GSD's own files that are checked in to the project.

It also names what only the owner can decide: a phase that is under way, phases GSD left unticked, a roadmap that began again at phase 1 for a later milestone.

Convert

Rewrite three files, keep everything else

The roadmap, the requirements and the state are rewritten in the format the phase tool reads. Phase numbers, titles, goals, dependencies and success criteria are kept. A requirement keeps its id with REQ- in front, so a search for the old id still finds it.

GSD's constraints become draft rules in the manifesto and its key decisions become decision rows. Both are drafts: the owner reads them before they count. A record lists every file, every phase with the reason for its status, and every id that changed.

GSD hasAfter the move
Phase folders, plans, summaries, verificationsUntouched
STATE.md, ROADMAP.md, REQUIREMENTS.mdRewritten; the originals are in archive/gsd/
PROJECT.mdArchived; its constraints and decisions are carried as drafts
Milestones, retrospective, research, quick tasksLeft in place as history
/gsd-* commands and agents checked in to the projectRemoved, with your go-ahead. An install in your home folder is not touched

What you gain

Acceptance tests agreed and locked before the code, one tool that refuses a step whose files are missing, and a search of existing code before anything new is built.

What you give up

GSD's milestone commands and its autonomous runs across phases. A new stretch of work is new phases added to the roadmap.

Finished phases

A phase finished under GSD stays finished. It has no acceptance tests, and a decision row on record says so.

A phase under way

Moving between phases is simplest. A phase carried mid-way has no locked tests: they are written late, or waived by a decision the owner approves.

Tried on copies of nine real GSD projects, from 2 to 43 phase folders. Each converted and passed the phase tool's check, with no phase folder changed. One passed only once the check was told to leave the project's own skills alone. No project has made the move for real yet, and nobody has run a phase to the end after it.

For a project already in flight

Nothing has to be migrated at once.

  • Keep your paths. The destination and the settings are yours; the skills adapt to your folders, not the other way round.
  • Take one piece. Start with the component index alone (the agent can write the first one from your code), or one workflow, and add the rest later.
  • Keep what you have customised. Exclude the files you want to stay yours and move your project-specific rules into project.md over time.
  • Stay with your workflow. A project built around phases keeps phases; one built around milestones keeps milestones.

For a brand-new project

One more command after the sync writes the starter planning files: a roadmap with one placeholder phase, the project state, and the first decision on record (adopting the workflow). The first sync also writes a starter component catalog. Fill in your first phase and you can run it.

Still rough

  • One rules file per agent. A project that serves both Claude Code and Codex has to keep its own project.md identical in both places by hand.
  • A person's override is trusted. A recorded, approved decision can waive a missing file at a step. The tool does not second-guess it.
