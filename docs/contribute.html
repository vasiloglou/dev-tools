Contribute

Changes come in as pull requests. One person merges them.

The repository is public and contributions are welcome. Nothing reaches the main branch except through a pull request, and the maintainer reviews and merges each one.

How a change gets in

  1. Open an issue for anything larger than a fix

    Say what went wrong or what is missing. For a defect, include the command you ran and what it printed. A short discussion first saves a pull request that goes the wrong way.

    Issues on GitHub →

  2. Fork the repository and make a branch

    You do not need any access to this repository. Fork it, branch from main, and work there.

  3. Make the change and run the tests

    The tests cover the sync command and the scripts a project runs after a sync. They need Python 3.11 or newer.

    uv run --no-project --with pytest python -m pytest tests -q

  4. Open a pull request against main

    Say what changed and why, and link the issue if there is one. Keep it to one purpose, so it can be read and accepted in one go.

  5. Review the maintainer approves

    The maintainer, @vasiloglou, reviews every pull request and is the only person who can approve and merge one. You may be asked for changes before it goes in.

What makes a change easy to accept

The skill text is the product. Changing a sentence changes how an agent behaves in every project that takes the next update, so the bar is the same for prose as for code.

A script change comes with a test

The sync command, the state tool and the index script each have tests under tests/. A fix arrives with a test that fails without it.

A wording change says what prompted it

Name the run where the agent went wrong, or the sentence it misread. "Clearer" is not a reason anyone can check.

Shared skills stay general

A rule that only makes sense in one project belongs in that project's own project.md, not in the shared text.

Both agents read the same file

A skill is copied for Claude Code and for Codex byte for byte. Write it so it is correct for either.

Captures on this site are real output

If a change alters what a command prints, replace the capture with a new run. Do not edit the old one by hand.

The page that describes it is updated too

The site lives in docs/ as plain HTML with no build step. A change in behaviour and its description go in the same pull request.

How main is protected

  • Pull requests only. A change reaches main through a pull request with an approving review.
  • One reviewer. Every path in the repository is owned by the maintainer, and the review that counts is the owner's.
  • History is kept. The branch cannot be force-pushed or deleted.

This site is served from docs/ on main, so a merged change to a page is live a minute or two later.
