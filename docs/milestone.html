Milestone workflow

Plan the milestone once. Let the agent walk it, with a record of every step.

For work that is specified up front and has to be defensible afterwards. You approve a spec before any code exists, an independent reviewer attacks the result, and every finished phase leaves a record that is never edited again.

Three skills, three jobs

start-milestone

Turns requirements and leftovers from earlier work into a plan: phases with stable ids, what each must deliver, and how each will be proven. Drafts the spec for the first phase. Writes no code.

process-phase

Runs one phase of the plan: collects everything that binds it, writes the spec, stops for your decision, implements, has the result reviewed, and records it.

process-milestone

Walks the whole milestone: picks the next phase whose prerequisites are met, runs it, and at the end sweeps every open question and writes the closing record.

Hands-off, when you say so

Add auto=true and the agent records your approvals itself and keeps going through the phases of this one milestone:

process-milestone v2-search auto=true

That delegation is narrow on purpose.

  • Each approval is recorded as delegated, with the date and a fingerprint of the exact text approved. It is never written up as if you had read it.
  • It does not skip a required review, invent a result, authorize paid calls, publish, or merge.
  • It covers this milestone only and ends when you revoke it.

One phase, start to finish

The order is fixed. The one hard rule: nothing is implemented before the spec is approved.

  1. Harvest

    What binds a phase is spread over the plan: its own deliverables, the verification promised for it, design rules earlier phases paid for, open questions assigned to it, risks, and what earlier records left unresolved. The agent collects all of it into one table at the top of the spec, so nothing binding is left as "see the plan".

  2. Spec stops

    Exact formats, exact signatures, the list of rules, and the list of tests with their expected results. Before showing it to you, the agent checks that every requirement can be satisfied as written.

  3. Your decision stops

    You approve or amend. You also decide how you want to approve: by reading the spec, or by reading a set of worked example cases written first. Each open question assigned to this phase gets your ruling, dated, in the spec.

  4. Implement and verify

    Built in slices that each end with passing tests. The tests run are the ones the change can affect, chosen by what changed and who depends on it, not the whole history of the project. One rule has no exception: a declared behaviour with no test that can fail it does not ship.

  5. Adversarial review

    A separate reviewer, in a different tool, tries to break the change. Each finding is reproduced before it is believed, and each fix comes with a test shown to fail on the old code. Findings are sorted into blocking, hardening and completeness before anything is fixed; completeness is deferred by default.

  6. Refactoring review

    One question, answered in writing: what did this work reveal about the existing structure that should change? The answer is either the refactors that were done, or "none needed" with the argument. A refactor seen and postponed becomes an open question with a target, never silent debt.

  7. Record and commit

    The phase is finished when its record exists: the commands that were run and their exit codes, word for word; a fingerprint of each file the claim rests on; what the result does not establish; and what is still open.

Records that cannot be quietly rewritten

Records are numbered and append-only. A correction is a new record that cites the one it corrects. What a milestone claimed, and on which exact files, stays readable long after the session that produced it.

What the independent review is for

In that same trial, the function passed all 25 of its own tests. A second agent, in a different tool, was then asked one thing: find where a claim about this change is false.

It found one

The plan claimed the function works for a whole number of any size. The reviewer tried one more than 4,300 digits long, and the function crashed.

The workflow then did what it always does with a finding: reproduce it first, write tests that fail on the old code, fix, and run again. The reviewer's words are kept exactly as written, beside a note that the fix itself has not been reviewed.

# notes/phase-DT1-codex-review.md (excerpts)

for integer string conversion

Reproduced: yes
Class: blocking

Red before the fix, observed: 2 failed, 27 passed
After the fix, the same command: 29 passed

Counts: 1 finding, 1 blocking, 0 hardening,
0 completeness, 0 self-inflicted.

Knowing when to stop reviewing

Repeated review of the same document does not keep improving it. Each round of repairs creates new text, and the next review finds problems in that new text. The workflow measures this and stops.

Across review rounds on one document, two numbers are computed:

  • the share of findings that attack text the previous repair wrote;
  • one reviewer's count of findings from round to round.

When more than half of the findings are about the previous repair, or when the count stays flat for two rounds while the findings get less serious, review stops. The next step is to build it: an implementation answers in seconds the questions that reading argues about for days.

The number of rounds allowed is written down before round two, so the stopping point is not chosen after seeing the results.

Two lanes. Not everything earns this weight. Routine, reversible work goes in the fast lane: edit, run the focused tests, done, no record. The evidence lane, with its reviews and records, is for a finished phase, a changed contract, or a decision that is hard to undo.

One reviewer is one reviewer. A record never calls a single review a panel, and never claims a review over text that changed after the reviewer read it.

Phase workflow or milestone workflow?

They answer different needs, and a project picks one. Both come from the same place and are installed the same way.
