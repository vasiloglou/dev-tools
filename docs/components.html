Component index

A map of what your code already does, that an agent reads before it writes.

An agent starts every session knowing nothing about your codebase. Without a map it writes a second date parser, a third retry helper, a fourth way to format a file size. The component index is that map: searchable by what the code does, and kept honest by a check.

Search by capability

"Is there already something that does this?"

The agent asks in plain words before it plans new code. The answer names the component, the file, and the function to call.

In the phase workflow this is not optional: each plan has a Reuse section that records what was searched for and what was found, and you see it when you approve the plan.

A match names the component, the file and the function, with its line. No match says so plainly, and says it is not proof that nothing exists.

Two layers

People write the meaning. The tool writes the details.

The catalog has one short entry per component, written by hand: what it is for, the verbs it covers, which files belong to it.

Everything else is generated from the source: every function with its signature and one-line summary, and which component uses which. The same search can also cover the libraries the project has installed. Generated pages are never edited by hand, so they cannot drift from the code.

The purpose, verbs, files and tests were written by hand. The two lines saying what it uses and what uses it were generated.

Kept honest

It notices when the code moves on

Add a file and the check fails: first because the index no longer matches the source, and then, in its strict form, for as long as no component has claimed the file. Closing a phase runs the strict check, so the map is complete at the start of the next phase.

shelf · a new file appearscaptured
$ git status --short src
?? src/shelf/export.py

$ components write && components --check --strict
no component: src/shelf/export.py (add it to the modules of an entry in docs/components/COMPONENTS.md)
exit code 1

A new file is added and the index regenerated. The strict check still fails, and names the file, until a component claims it.

Starting it, keeping it, and looking at it again

A map is only worth having if someone draws it and keeps it true. The skill gives the agent three more jobs: build the index for a codebase that has none, check it against every change, and now and then review the whole thing against the code.

Build

No index yet? The agent writes the first one.

The tool does the mechanical half: it lists every file, class and function straight from the source, and prints a stub for each file with its summary, what it imports and what imports it.

The agent does the half that needs reading. It opens the code, groups files into capabilities, and writes each entry in the words someone would search for. A stub left as it came is refused. Whatever cannot be finished in one sitting is recorded in a list that is only allowed to shrink.

It ends by using the map: it searches for things a newcomer would ask for, and fixes the entries until they are found.

Every change

Checked against what the change touched

Before a pull request, one command compares the index with the files the branch changed.

  • Fail: a new file no component has claimed, or generated pages that no longer match the source.
  • Warning: new code that calls a component marked as retired or as a duplicate.
  • Reread: the code of a component changed and its description did not. A script cannot tell whether a sentence is still true, so it names the entry and the agent reads it beside the change.

The same command runs in automated checks; an example job for GitHub ships with the skills. Both workflows run it: the phase workflow when a phase closes, the milestone workflow before a phase is recorded.

shelf · a branch that adds one file and changes anothercaptured
$ git status --short
 M src/shelf/scan.py
?? src/shelf/export.py

$ components write && components changed --base develop

exit code 1

$ git diff -U0 docs/components/COMPONENTS.md | grep '^[+-]- does'
-- does: Walk a folder tree and list every regular file with its size in bytes
+- does: Walk a folder tree and list every regular file that is not hidden, with its size in bytes
+- does: Write the file list as CSV text with a readable size column (to_csv)

$ components write && components changed --base develop
changed against develop (d74dcb8): 5 file(s) differ; 0 to fix, 0 warning(s), 0 to reread

The new file has no component, and the scan now skips hidden files while its entry still says "every regular file". The agent adds one entry and corrects the other; the check is clean.

Review

From time to time, the whole index against the code

Checks keep the form right. They do not notice that two components do the same job, that something is no longer used, or that a description has drifted. A review does.

It starts from a list of leads the tool can see: descriptions older than their code, the same name written in two places, components that import each other, retired code that is still called. Each lead is a place to look, not a finding.

Then the agent rereads every entry beside its code, repairs the index, and writes down the code changes it would suggest, each one checked in the code, sized, and with what could break. It changes no code. You decide which suggestions become work.

Three of the five suggestions in the report an agent wrote for this project in a trial run, word for word (the columns for location and size are left out). The first was not planted: the agent found it by reading the code. It repaired the index and changed no source file.

Tried on real code. In trial runs on copies of two real projects, an agent built a complete index from nothing for a package of 298 files and 130,000 lines: 208 components and 8 end-to-end flows, every file assigned, using twelve reader agents and about three million tokens. Another reviewed one area of an existing index on a project of 1,266 files: 17 entries reread, 15 repaired, 14 code changes suggested. The trials also turned up 73 defects in the skill and its tool; most are fixed, and the rest are listed as known limits.

What it changes in practice

MomentWithout the indexWith it
Scoping a phaseThe agent greps for a few names it guessesIt lists the capabilities needed and looks each one up; you see a table of what exists
Planning"Add a helper to format sizes""Reuse humanize_bytes from the units component"
Changing shared codeCallers found by search, some missedThe component's used by list is the set of callers to keep working
Reaching for a libraryA new dependency, or a hand-written copyThe index of installed libraries shows what is already available
Adopting it on existing codeNobody has time to write the map, so there is noneThe agent drafts it from the source and the code, in batches, and records what is left
Opening a pull requestThe description of a component quietly goes out of dateThe check names each component whose code changed and whose description did not
Months laterTwo helpers for the same job, and code nobody callsA review lists them as suggested changes, with evidence, for you to accept or reject
FinishingNew files nobody will find againEach new file must be given a component before the phase can close; the strict check names any that were missed

It reads source text only. The index is built by parsing files, never by importing or running your code, so it works on a project that does not currently start.
