Why it exists

Writing code got cheap. Knowing it is right did not.

A coding agent can produce a day of work in minutes. Someone still has to know that it does what was asked, that it did not rebuild or break what was already there, and that the next session can carry on from it. dev-tools is a process that makes those three things checkable.

The problem is not the code

An agent is fast and capable, and it starts every session with no memory of the last one. It has been asked to finish a task, and it is good at reaching whatever signal says the task is finished. When that signal is "the tests pass", the shortest way there is sometimes to change the test.

This is not bad intent. It is what happens when the only rules are sentences in a prompt. A sentence in a prompt is a request, and over a long task a request gets forgotten or traded away for progress.

There are two usual answers. Read every line the agent writes, and lose the speed you wanted it for. Or trust it, and find out later. dev-tools is a third: you decide a few things yourself, at fixed points, and checks hold everything in between.

Why it matters

The more work agents do, the less of it a person reads line by line. Something has to stand in for the reading. It is either trust or a record.

Speed with no record moves the cost to later. It shows up as a second helper for a job that already had one, a test that asserts less than its name says, and a decision nobody can explain six months on.

A record is worth having only if it is produced as the work happens and cannot be quietly rewritten afterwards. That is most of what these skills do: they make an agent leave one, and they refuse to move on when it is missing.

Nine ideas the rest follows from

The skills are long and specific. These are the short reasons behind them.

  1. A rule is a check, not a request

    What matters is enforced by a small script that can refuse. The state tool will not skip a step. The lock notices a changed test. The index check names a file no component has claimed. The sync will not overwrite your edit. The agent is still told the rule in words, but the words are not what holds it.

  2. Decide what "done" means before any code exists

    In a phase, the acceptance tests are written first, shown to fail for the right reason, approved by you, and locked. In a milestone, you approve a spec with its list of tests and expected results. Either way the target is fixed while it is still cheap to argue about, and it cannot move to meet the code.

  3. Try the idea before building it

    A phase starts with a prototype on real data, with a measurable target and a time limit. Each goal gets a verdict: go, pivot or kill. A goal that does not hold up is dropped there, before a test or a line of product code exists for it.

  4. Reuse before build

    An agent that cannot see the codebase writes what is already there. So it asks the component index first, and the plan you approve has a section that says what was searched for, what was found, and why anything new is justified.

  5. The repository remembers, so the agent does not have to

    Decisions, plans, test results and the current step are plain files under version control. Nothing important lives in a conversation. A new session, a different agent or a person reads the same files and knows where things stand.

  6. A person decides, at a few fixed points

    Scope, the tests, the plan and the close are yours. Between those points the agent works without stopping to ask. Merging and releasing stay your decisions. When you hand an approval to the agent, the record says it was delegated. It is never written up as if you had read it.

  7. Evidence, and its limits, in writing

    "Done" is a command, its exit code, and the files it ran on, not a sentence from the agent. A record also says what the result does not establish. One review is called one review, never a panel, and it does not cover text that changed after the reviewer read it.

  8. Process is a cost. Spend it where it buys something

    A process that reruns everything at every step gets abandoned. So focused tests run while working, results are reused for the same code, and the full suite runs once per phase. Review stops when most of its findings are about the previous round of repairs. Routine, reversible work takes a fast lane with no record at all.

  9. Plain files, owned by the project

    The skills are text and a few small scripts, copied into each project and committed there. There is no package to install, no service to run, and no dependency on this repository. What is specific to your project goes in one file you own, and it wins over the shared text.

What it is not

Not an agent

It is instructions and checks for the agents you already use. It runs nothing by itself and calls no model.

Not a framework

Nothing is imported by your product and nothing ships with it. Remove the copied files and your code is unchanged.

Not a guarantee

A check catches what it was written to catch. A person's recorded decision can waive a missing file at a step, and the tool does not second-guess it.

Not finished

It is a working prototype. In the trial runs so far the approvals were simulated. The home page says what has been done and what has not.

Who it is for

A developer or a small team that already works with Claude Code or Codex on a real codebase, and wants the agent to do longer stretches of work without giving up the say on scope, tests and merging.

It suits a project with a roadmap or a specification to work from. It is too much for a one-off script or an ad-hoc fix, and the skills say so: a phase runs only when you invoke it.
