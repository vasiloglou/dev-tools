For Claude Code and Codex

A coding agent that works like your most careful engineer.

dev-tools is a set of skills that give an agent a development process: agree on the goal, write the tests first, reuse what already exists, stop for your approval, and leave a record the next session can pick up.

Agents are fast. Left alone, they are also careless in four familiar ways.

Each one has a specific remedy here, and each remedy is enforced by a check, not by asking the agent nicely. Why it is built this way →

Without a process

The test gets changed until it passes

With dev-tools

Tests are agreed and locked before any code is written. A changed test is detected.

Without a process

Code that already exists is written again

With dev-tools

The agent searches a map of the codebase first, and the plan you approve shows what it found.

Without a process

Every session starts from zero

With dev-tools

Where the work stands is written in the repository. Any session, any agent, continues from it.

Without a process

"Done" means the agent said so

With dev-tools

Done means the agreed tests pass, one full run is on file, and you approved the steps that are yours.

What it looks like

The terminal frames on this site are real output, captured from a small demo project called shelf (a command-line tool that lists the files in a folder) that was taken through the process. The output is untouched. Only the long paths of the three helper scripts are shortened in the command lines, to phase-tool, components and devtools-sync.

01

Tests are locked before code exists

You approve the acceptance tests, and a fingerprint of each one is recorded. If a test is later weakened to get a passing run, the check fails and names the file.

How a phase runs →

shelf · a locked test is changedcaptured
$ git diff -U0 tests/acceptance/p03_size_report/test_report_cli.py | tail -3
@@ -32 +32 @@ def test_last_line_is_the_total(sample_tree, capsys):
-    assert total == "5 files, 12.0 MB"
+    assert total.endswith("MB")

$ phase-tool check --testlock 03
phase_tool.check: FAILED
error CHECK_FAILED: 1 issue(s) found
hint: fix the listed issues
checks: ["testlock"]
- tests/acceptance/p03_size_report/test_report_cli.py:0 [testlock] locked test modified
exit code 1

$ git checkout -- tests/acceptance/p03_size_report/test_report_cli.py

$ phase-tool check --testlock 03
phase_tool.check: ok
checks: ["testlock"]

An assertion is weakened, the check fails and names the file; the file is restored and the check passes.

02

Steps cannot be skipped

Every move from one step to the next goes through a small state tool. It refuses to jump over a step, and it will not approve a step while the file that step should have produced is missing, or while the phase depends on one that is not finished.

shelf · trying to skip aheadcaptured
$ phase-tool status --brief
phase_tool.status: ok
current_phase: 03
phase_status: not_started
active_step: None
next_step: discuss

$ phase-tool advance --to implemented
phase_tool.advance: FAILED
error INVALID_TRANSITION: not_started -> implemented is not allowed
hint: allowed: context_approved
phase: 03
from: not_started
to: implemented
exit code 1

$ phase-tool complete --phase 03
phase_tool.complete: FAILED
error NOT_VERIFIED: phase 03 must be the current phase with status verified
hint: run the Verify step and advance --to verified first
exit code 1

The phase has not started. Marking it implemented, or closing it, is refused.

03

Existing code is found first

Before planning anything new, the agent asks the component index what the project can already do. The answer is a file and a function to call.

How the index works →

shelf · asking what already existscaptured
$ components search human readable size
component format.sizes: Format a byte count as a short human-readable size such as 1.5 kB (humanize_bytes)
module src/shelf/units.py: Turn byte counts into short text a person can read.
component fs.scan: Walk a folder tree and list every regular file with its size in bytes
module src/shelf/scan.py: Walk a folder and list the regular files in it.
coverage: 4/4 src/shelf modules assigned to components; external: none

$ components search checksum
no component matched: this is not proof that nothing exists; search modules/ and git grep
coverage: 4/4 src/shelf modules assigned to components; external: none

A match names the component and the file. No match says so plainly, and says it is not proof that nothing exists.

04

Work in the order that suits you

Phases are numbered, but only their stated dependencies decide what may start. Here phase 3 is started before phase 2, with the decision on record, while phase 4 is refused because it depends on work that is not finished.

shelf · starting phase 3 before phase 2captured
$ phase-tool activate --phase 3 --dec DEC-002
phase_tool.activate: FAILED
error UNKNOWN_DEC: DEC-002 is not a row in .planning/DECISIONS.md
hint: write the DEC row (reason, human approval) before using it
exit code 1

$ phase-tool activate --phase 4 --dec DEC-002
phase_tool.activate: FAILED
error NOT_ACTIVATABLE: phase 04 has incomplete dependencies
exit code 1

$ phase-tool activate --phase 3 --dec DEC-002
phase_tool.activate: ok
phase: 03
dec: DEC-002
phase_status: not_started

First try: the decision is not on record yet. Phase 4 is refused because it depends on unfinished work. Phase 3 starts once the decision is written down.

05

One process for every project, and for both agents

The skills are kept in one place and copied into each project. An update never overwrites a file you changed without telling you.

How a project takes it → · Coming from GSD →

$ echo 'Skip the full run when in a hurry.' >> .claude/skills/process-phase/references/verify.md

$ devtools-sync check --project .
.claude/skills/process-phase/references/verify.md: differs from the receipt
29 managed file(s), 1 problem(s)
exit code 1

$ devtools-sync apply --project .

nothing written; 1 file(s) refused
exit code 3

Someone adds a line to a synced rule. The check reports it, and an update refuses to overwrite it.

You stay in charge at the points that matter

A phase has seven steps. The agent does the work in all of them and stops for your decision at four.

  1. Orientreads where things stand
  2. Discusssettles scope, tries a prototype
  3. Specifywrites and locks the tests
  4. Planfinds what to reuse
  5. Implementone failing test at a time
  6. Verifyone full run
  7. Closerecords, hands back

ends with your approval

Two workflows. A project picks the one that fits.

Both are installed the same way and both use the same component index.

Phase workflow

For a product growing along a roadmap. Each phase starts with a short prototype to see whether the idea holds, then locks its tests, then builds. You approve four times per phase.

Read about phases →

Milestone workflow

For work specified up front that must be defensible later. A spec you approve before any code, an independent reviewer who attacks the result, and numbered records that are never edited. Can run hands-off when you delegate.

Read about milestones →

Component index

A searchable map of what the code already does, part written by people and part generated from the source. The agent can build it for existing code, check it with every change, and review it from the top. Optionally, the project's own rules about what may use what are checked with every change.

Read about the index →

Where it stands

dev-tools is a working prototype. What has been done, and what has not:

  • Run end to end. The phase workflow built one real feature in the demo project shown on this site. Each workflow was also tried inside an existing project in mid-flight, by swapping in the shared skills and carrying a small mock piece of work from start to finish.
  • Approvals were simulated in all of those runs. No person sat at the gates.
  • Found and fixed. Those runs turned up 44 defects in the tools and the skill text. Most are fixed. A project in mid-flight keeps its old behaviour through one setting, and a brand-new project is set up with one command.
  • On trial. The project-rules check (component index, "Project rules") has run on two codebases and no project has adopted it yet. It needs GND 0.2.0 or newer. Two checks of the plans against the agreed tests and of a change against the plans are advisory until they have run on real projects.
  • Moving from GSD was tried on copies of nine real GSD projects; each passed the phase tool's check afterwards. A review then found 27 problems in the move and in what follows it; the 15 that mattered most are fixed and tested, and 12 smaller ones are open. No project has made the move for real yet. What the move does.
  • Planned: running independent phases as parallel tracks with their own state, and a skill that finds what agentic work leaves on your disk (old working copies, caches, downloaded models).
