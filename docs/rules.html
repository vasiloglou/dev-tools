Project rules · optional, a trial

The index says what the code is. GND says whether that is allowed.

The component index knows which part of your code uses which. It has no way to say that the core must not import the command line. A project that wants such rules writes them down once, and dev-tools hands the facts and the rules to GND, a separate checker, to judge. This page says what GND adds, what it costs, and what a pass does not show.

What GND is

GND is a separate open-source project from the same author. It checks a set of facts against a set of rules. For each rule it says that the rule holds, that it is broken and which facts break it, or that it cannot be decided.

The checking is deterministic. The same facts and the same rules give the same answer every time, and no language model takes part in it.

GND was built to check what agents produce in data applications, and it does much more than dev-tools asks of it. dev-tools uses one command, gnd check.

Why dev-tools does not judge the rules itself

The checks dev-tools ships are about its own process: is this step done, was this test changed, has a component claimed this file. Each is a few lines of Python with one fixed question.

A project's rules about its own architecture are different. Every project has its own, they change, and nobody here knows them in advance. Writing one more hand-made check for each would never end.

That is a job for a rule engine: the rule is data, and one engine judges any rule. GND is such an engine, so dev-tools states the facts and leaves the judging to it.

How the two fit together

dev-tools produces the facts and prints the result. The project writes the rules. GND does the judging in the middle.

StepWhoseWhat happens
Factsdev-toolsThe index script writes the catalog and the import graph as plain facts: which components exist, their status, area and tests, which one uses which, and which imports lie inside a loop. This step needs no GND.
RulesThe projectTwo small files beside the catalog, written by hand. layers.toml gives each area a rank or names pairs that are never allowed. rules.json holds the rules; four starter rules ship.
JudgingGNDThe check script turns the facts and the rules into the form GND reads and runs gnd check, on the branch and on the base it started from. GND marks each broken rule as new or standing.
Reportdev-toolsThe script prints what the change added: a failure for a must rule, a warning for a should rule, each with the components, one import behind them, and the remedy the rule's author wrote.
# docs/components/layers.toml
[rank]            # a component may use components of its own rank or a lower one
core = 0
store = 1
cli = 2

[[forbid]]        # one pair that is never allowed, whatever the ranks
from = "store"
to = "report"

Layers need no rule to be written. This example is from the guide that ships with the skill.

# one entry in docs/components/rules.json
{
  "id": "canonical_does_not_use_experimental",
  "level": "must",
  "remedy": "A canonical component uses an experimental one: finish it first, or mark the caller experimental",
  "type": "guarded",
  "antecedent": [
    {"fact_type": "component_uses", "bind": {"caller": "$a", "callee": "$b"}},
    {"fact_type": "component_has_status", "bind": {"component": "$a", "status": "canonical"}}
  ],
  "consequent": {"absence": {"fact_type": "component_has_status", "bind": {"component": "$b", "status": "experimental"}}}
}

A rule of the project's own, also from the guide. It reads: for every canonical component that uses another, the other must not be experimental. The part from type down is GND's constraint language.

What GND adds

Six things the check has because the judging is GND's.

A rule is data, not code

A project adds a rule by writing one entry in a file. No Python is written and nothing in dev-tools changes. The rule can be read, reviewed and changed like any other line in the repository.

The same answer every time

No model reads the code and forms an opinion about its architecture. This is the first idea on the Why page, a rule is a check and not a request, applied to the shape of the code.

Only what the change added

GND judges the base and the branch by the same rules and marks each finding new or standing. An existing project can switch the check on without first repairing its history.

A finding names its facts

A failure is not "architecture violated". It names the rule, the two components, and the import between them, and it repeats the remedy the rule carries.

"Cannot decide" is not a pass

A rule GND could not decide is reported under that rule's own level. A check that did not run exits with its own code, and a report the script cannot read stops it.

The engine is someone else's job

dev-tools' part is small: state the facts, call GND, print the report. The constraint language and the comparison with the base live in a project whose whole purpose is checking facts against rules.

Rules about plans · a trial

The same rules file can judge a phase's plans

For a project on the phase workflow. Before you approve the plans of a phase, the plans are read as facts too: which task names which file, which components a plan says it reuses, what kind each task is. Joined with the component index, a rule can then say what a plan may do.

One such rule ships: a task that changes a file of a component the plan's Reuse section does not name. A project adds its own, for example that a task changing the billing area must be one a person checks.

The checks the workflow fixes for every project, such as two parallel plans that name the same file, are not here. They are plain Python and need no GND. This is only for rules a project writes itself.

What has and has not been shown. These rules have run on plans written to test them and on no real project's plans, and no step of the workflow requires the check. A rule sees only what a plan writes down: a task that changes a file its plan does not name breaks no rule here.

What it costs

The skills are plain files with nothing to install, and that is one of the ideas they are built on. GND is the one exception, which is why it is optional.

  • Nothing depends on it. Without GND the check prints skip: and passes. Both workflows, the index and the export of facts work the same.
  • One install. GND is on PyPI as get-nick-done, under the Apache 2.0 licence, and needs Python 3.11 or newer. A project that would rather not install it sets the command to run it through uvx.
  • A known version. The check needs release 0.2.0 or newer and was last tried with 0.3.0. It stops on a report in a version it does not know.
  • In automated checks, say it is required. With --require a missing GND is a failure, so a job cannot pass by not running. An example job for GitHub ships in examples/rules-check.yml.
uv tool install get-nick-done==0.3.0
python3 .claude/skills/components/scripts/rules_check.py init
python3 .claude/skills/components/scripts/rules_check.py check --base main

Install, write the two starter files, check a branch against its base.

What a pass does not show

  • Only what the index sees. The facts come from the catalog and from import statements. An import made at run time from a name in a string breaks no rule, and neither does a call through a registry.
  • Component ids, not folders. A file is judged by the component that lists it, wherever it sits on disk.
  • A regrouping can look new. Moving a file from one component to another makes its old imports new facts.
  • The index must be right first. A file no component has claimed has no facts, so its imports break no rule. The index checks run before this one.
  • What was already broken. Against a base, a pass says nothing about standing items. The summary line counts them.
  • The rule is only as good as its sentence. GND checks the facts against what was written, not against what was meant.

Where it stands

This check is a trial. It has run on two codebases and no project has adopted it yet. The agent is told to use it where you asked for it and not to add it to a project unasked.

What has not been shown yet is the part that matters most: an owner acting on a finding, and someone writing a rule of their own from the guide.
