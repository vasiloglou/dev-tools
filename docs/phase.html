Phase workflow

One command runs a phase. Seven steps keep it honest.

You keep a roadmap of phases. You tell the agent which one to run. It works through the same seven steps every time, stops for your approval at four of them, and cannot move on until the step before is really done.

The skill only runs when you invoke it. It never starts a phase because a conversation happened to mention one.

The seven steps

Each step needs the one before it and leaves a named file behind. A marked step ends with a stop: the agent shows you what it produced and waits.

  1. Orient

    The agent reads where the project stands: the roadmap entry for this phase, the decisions and lessons recorded so far, and your project's own rules. It switches to the phase's branch and resumes unfinished work instead of starting over.

    Leaves behind: nothing. It only reads.

  2. Discuss you approve

    The agent finds the choices the roadmap left open and asks you about them in small batches, each with a recommendation. Then it tries the idea by hand before anyone commits to it: it sets a measurable target, takes a baseline on real data, runs a prototype with a time limit (two hours by default), and gives each goal a verdict of Go, Pivot or Kill.

    A goal that did not hold up is dropped here, before tests or code exist for it.

    Leaves behind: the phase context (your decisions, each marked locked, deferred or left to the implementer) and the prototype report with its verdicts.

  3. Specify you approve

    The agent writes acceptance tests for the targets that held, and runs them to confirm they fail for the right reason. Then the tests are locked: a fingerprint of every test file is recorded. From here on, a change to a locked test is detected, and only your recorded decision can re-lock it.

    Leaves behind: the acceptance tests, the record of their failing run, and the lock file.

  4. Plan you approve

    Before planning new code, the agent searches the component index for every capability the phase needs and writes down what it found. Each task in the plan names the tests it turns green and the files it may touch.

    Leaves behind: one or more plans, each with a Reuse section.

  5. Implement

    The agent supervises; a separate coding agent writes the code, one failing test at a time. Each round is checked before it is accepted: a round that touched a file outside its list, or changed a locked test, is rejected whole. Independent tasks can run side by side in separate working copies.

    Leaves behind: the code, one commit per task, and a short summary of what was done and what deviated from the plan.

  6. Verify

    The full test suite runs once, on the finished code. Results from earlier focused runs are reused, not repeated. A gap is a real failing test or an unmet exit criterion, and it sends the phase back to planning for that gap only.

    Leaves behind: the verification report and the log of the full run.

  7. Close you approve

    The agent records the lessons, updates the component index with any new code, and marks the phase complete. Merging to your base branch and releasing stay your decisions.

    Leaves behind: an updated roadmap and project state, ready for the next session, which may be a different agent on a different day.

What stops an agent from cutting corners

The steps are enforced by a small state tool that ships with the skill. The agent calls it for every transition; it refuses when the work is not there. These are captures from the demo project.

It cannot skip ahead

A phase that has not been discussed cannot be marked implemented, and it cannot be closed before it is verified. The tool names the only move that is allowed.

shelf · trying to skip aheadcaptured
$ phase-tool status --brief
phase_tool.status: ok
current_phase: 03
phase_status: not_started
active_step: None
next_step: discuss

$ phase-tool advance --to implemented
phase_tool.advance: FAILED
error INVALID_TRANSITION: not_started -> implemented is not allowed
hint: allowed: context_approved
phase: 03
from: not_started
to: implemented
exit code 1

$ phase-tool complete --phase 03
phase_tool.complete: FAILED
error NOT_VERIFIED: phase 03 must be the current phase with status verified
hint: run the Verify step and advance --to verified first
exit code 1

The phase has not started. Marking it implemented, or closing it, is refused.

It cannot bend a test to pass

Once tests are approved, their contents are fingerprinted. Here one assertion is weakened from an exact value to "ends with MB". The check names the file, and the plan cannot be approved until it is put back. Changing a locked test takes a decision you approve, recorded with an id, in its own commit.

A coding round that strays is rejected

During Implement, each round of the coding agent gets a list of files it may touch and a size limit. A check runs after every round. Here the first round is too large and leaves files outside its list; later, a round that edits a locked test is caught the same way. A rejected round is thrown away, not patched up.

Phases do not have to run in order

The roadmap numbers phases, but only the depends on line of each phase decides what can start. Two phases that depend on the same finished phase are independent, and either can go first. Starting out of numeric order takes a one-line decision on record, so the choice is visible later.

Testing without ceremony

A process that reruns everything at every step gets abandoned. This one has a written policy against that:

  • Focused tests while working. One failing test, the smallest fix, then that test and its neighbours.
  • Results are reused. A handoff, a status change or a documentation commit does not invalidate a result for the same code.
  • One full run per phase. It happens in Verify, on the finished code.
  • No review loops by default. Code review is optional. A failed test leads to a fix, not to a round of reports about the failure.

Your project's own rules

The shared skill knows nothing about your product. Rules that only make sense in your project (an invariant that must never break, an extra check before release, the command that runs your tests) go in one file your project owns, references/project.md, beside the skill. The agent reads it in Orient, and it wins over the shared text on anything project-specific. Updating the shared skill never touches it.
