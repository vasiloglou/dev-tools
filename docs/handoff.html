Hand-offs

Move unfinished work to another assistant or machine, with what the session knew.

Git carries the code. It does not carry the goal, what was verified, the next step, what you decided, or the job still running on another host. Two skills carry those: dev-handoff when work leaves, and dev-takeover when it arrives. They work with either workflow, and on a branch that uses neither.

Leaving

One note per branch, and a check that says what would be lost

The agent commits the work, then asks the script for the branch's note. The script writes what it can read off the checkout, and the agent fills the rest from the session.

You say who continues and where. That sets the level: the same assistant on the same machine needs a short note, another assistant needs one that stands alone, and another machine also needs everything pushed.

A new note starts with every section empty, and the check says so.

The note

The tool writes the snapshot. The agent writes what only the session knows.

The snapshot is regenerated on every write: the branch and its commit, what is uncommitted, what git ignores, and what the receiver has to read because its assistant does not load it by itself.

Below it are eight sections for the one who is leaving: the goal, what works and how it was checked, the next step, open questions, decisions already made, your standing instructions, what runs or lives outside git, and the commands to continue. A section already filled is kept when the snapshot is refreshed.

A check that can refuse

Not done until the work can actually travel

With the sections filled, the check still fails: two files are uncommitted and the branch was never pushed. For another machine those are losses, so the check exits 1.

After a commit and a push it passes. What is left is a reminder, not a failure: two paths git ignores exist only here.

It also fails on a required section that is missing or blank and on a note that contains something shaped like a key, and for a receiver that is not Claude Code it points out a skill named as a slash command.

What git ignores

Run output and local data go checkout to checkout

A push does not move the files git ignores: benchmark output, transcripts, a local database. The script lists them by kind and copies the ones this branch produced straight to the other checkout, over ssh for another machine. Nothing ignored is ever added to git.

Environments and caches are rebuilt on the other side; they are named, not carried. A file that looks like a key is never copied unless you ask for it by flag, and that holds for one inside an ignored folder too. A file the other checkout tracks in git is never copied over. A copy is a dry run until --yes.

$ handoff carry --dest ../shelf-second
carry to ../shelf-second: 1 path, 0.3 MB; NOT copied: dry run; pass --yes to copy
  runs/
  skipped (key): .env

The benchmark run is offered; the .env file is held back; the virtual environment is named as something the other side rebuilds.

On the other side

The receiving agent does not start from the conversation, because it never saw it. It starts from the note, and it checks the note against the code before trusting it.

Arriving

Which hand-off, and is this machine ready for it?

With no branch named, the agent lists the hand-offs on local and remote branches and asks you which one to take over. It does not pick one itself.

On the branch, one report says whether this checkout has the commit the note was written at, which ignored files the note was written with are missing here (every one, including those after the 25th that the note does not list for a reader), and what the machine lacks. A project names what its machines need (tools, an environment, key files) in the script's settings. A missing tool or environment means not ready; so does a note with no next step.

Ready

Fetch what is missing, then continue from the next step

The receiver can fetch the ignored files itself. For another machine the script is sent over ssh to list them there, so the old machine needs no copy of it, and what that machine lists is held to this checkout's rules: only paths this checkout ignores are copied.

Then the agent reads the whole note, runs the tests it names, and tells you what differs: the code wins. Only then does it continue from the next step.

How much to hand over

LevelCaseThe receiver already hasThe note must add
1The same assistant on the same machine: another account, or a fresh sessionThe checkout, the project's files, the skillsGoal, done so far, next step, open decisions. No push needed
2Another assistant or a person, same machineThe checkout. Not your skills, your memory or the sessionEvery section, standing alone: paths and commands, not skill names
3Another machine, or a cloud sessionOnly what is pushedThe same, plus everything committed and pushed, and what lives outside git

What it changes in practice

MomentWithout a hand-offWith it
Switching from one assistant to anotherYou retell the task, and forget the instruction you gave an hour agoThe note carries your instructions for this work, written out in full
Moving to another machineAn uncommitted file, a stash or an unpushed commit stays behindThe check fails until none of them would
Results that are not in gitThe run is repeated, or its numbers are quoted from memoryThe files are listed, and copied to the other checkout when you say so
A job still running elsewhereNobody remembers it until the bill arrivesThe note says where it runs and how to check and stop it
Picking the work upThe new session trusts whatever summary it was givenIt runs the note's tests first and reports what differs
A phase paused mid-taskThe workflow's own pause file, which a different assistant may not know to readThe note points at it and adds what it does not hold; the phase continues through its workflow

The note informs. It approves nothing. A paid run, a deployment, a merge or a release that the note mentions needs your yes again on the other side. The script never commits, pushes or deletes, and the note is removed in the last commit before the pull request.
